# 结果分析

该部分聚焦于盘古 - 1B 模型的服务吞吐量优化，核心技术手段涵盖 chunk prefill、并发、Radix Attention等。我们系统探究了各类优化技术的独立效能与作用机制，并通过多策略协同融合，将模型吞吐量提升xx倍。

## chunk prefill

chunk prefill 是大模型推理中针对长序列处理的关键优化技术，针对上下文填充（prefill）阶段，将输入的长文本序列切分为多个小 chunk（数据块）分批完成 prefill 计算，而非一次性处理整段长序列，其加速核心在于拆分长序列计算任务以降低单次计算对 NPU 等硬件的内存峰值占用，避免因内存不足引发的数据频繁换入换出或计算阻塞，同时可充分利用硬件批处理能力并行处理多个 chunk，提升计算资源利用率，减少单次 prefill 的计算延迟，最终缩短大模型端到端推理耗时。

我们在INPUT_LEN=8192 OUTPUT_LEN=32 NUM_PROMPT=100条件下测试了有无chunk prefill支持，以及不同chunk大小下的吞吐量，结果如下：


| no chunk | 2048  | 8192  |
| -------- | ----- | ----- |
| 41.67    | 40.07 | 46.41 |

结果显示，无 chunk 方案的吞吐量为 41.67，chunk=2048 时吞吐量略降至 40.07（推测受分块调度 overhead 轻微影响），而 chunk=8192 时吞吐量显著提升至 46.41，较无 chunk 方案提升约 11.4%；这一结果表明，合理选择 chunk 大小可有效优化长序列推理吞吐量，其中 chunk=8192 能通过减少分块次数降低调度开销，同时充分发挥 KV 缓存复用优势，避免小 chunk 带来的 overhead 累积，而 chunk=2048 因分块较细导致调度成本抵消了部分优化收益，因此 chunk prefill 方案的最优性能需结合输入序列长度匹配 chunk 尺寸。

## 并发

在LLM Serving场景中，并发优化是指通过合理调控单GPU/推理实例同时处理的推理序列数量，充分挖掘硬件算力的核心优化手段。该优化能实现性能提升的核心逻辑在于：LLM单序列推理时，GPU的CUDA核心、内存带宽等计算资源利用率极低，大量算力处于空闲状态；而并发优化可通过同时承载多个推理序列，让硬件资源趋近饱和，摊薄单序列的调度、内存IO等固定开销；同时，批处理模式下模型权重只需一次加载到显存并复用，避免了重复的内存访问损耗，推理框架还可针对批量序列做算子融合、显存复用等底层优化，最终在不显著增加单序列延迟的前提下，大幅提升整体Token吞吐率，实现算力利用效率与服务吞吐量的双重提升。
我们在INPUT_LEN=1024 OUTPUT_LEN=128 NUM_PROMPT=1000条件下测试了不同并发度下的吞吐量，结果如下：


| 1     | 8      | 16     |
| ----- | ------ | ------ |
| 78.52 | 483.50 | 795.86 |

## Radix Attention

Radix Attention 是 一种基于基数树（Radix Tree/Trie）数据结构的 KV 缓存自动复用技术，核心用于解决 LLM 推理中传统独立 KV 缓存无法跨请求共享公共前缀的问题 —— 它通过基数树高效组织缓存数据，自动识别不同推理请求间的重复 prompt 前缀（如多轮对话历史、批量 few-shot 公共指令）并复用对应 KV 缓存，无需手动配置共享规则，既避免了重复计算带来的算力浪费，又减少了冗余缓存占用的显存空间，最终在多请求并发场景下显著提升推理吞吐量、降低显存开销，尤其适配批量推理、多轮对话等高频 LLM Serving 场景。
我们在INPUT_LEN=1024 OUTPUT_LEN=128 NUM_PROMPT=1000条件下测试了使用和不使用Radix Attention下的吞吐量，结果如下：


| w/o radix | w radix |
| --------- | ------- |
| 78.52     | 483.50  |
